## 本轮确认并修复

### 1. IPC 控制调用可能永久阻塞（高优先级）

`PipeEndpoint::ReadFrame()` 原来对所有读取使用无限等待。目标进程在注入后崩溃、卡死或只连接管道但不发送 Hello 时，`ShellIpcSession::Start()` 会一直卡在 Hello 回复；`TargetLink` 工作线程无法退出，关闭窗口也可能长时间卡住。

修复：

- `ReadFrame(timeout_ms)` 支持有限超时。
- Shell 控制请求使用 `ShellSessionOptions::control_timeout_ms`，默认 10 秒。
- Hello、Ping、普通控制命令和 Detach 都使用同一有限控制超时。
- 控制读写一旦超时或失败会把会话标记为 Disconnected，禁止复用已经可能出现半帧的字节流。
- Packet/Event 后台流保持可取消的无限读取，避免改变正常流式语义。

新增回归：无控制循环的静默 Target 在 50 ms 内让 Hello 失败，且测试确认不会阻塞 1 秒以上。

### 2. StartHook 检测失败仍继续安装 hook（高优先级）

`HeadlessCore::StartHook()` 捕获 `DetectWinsock(true)` 异常后只发 Fatal 事件，却继续调用 `hooks_.StartHook()`，会把“检测失败”误当作“可以安装”，造成错误状态或部分初始化。

修复：检测失败发 Fatal 后立即重新抛出；不会调用 StartHook，也不会设置 `hook_installed_`。

新增回归：检测异常时 StartHook 次数保持 0，状态保持未安装。

### 3. StopHook 失败却报告“已停止”（高优先级）

原实现先把 `hook_installed_` 设为 false，再吞掉底层 StopHook 异常并发送关闭状态。底层清理失败时，UI/调用方会看到“关闭”，但 detour 可能仍然存在。

修复：先执行底层 StopHook；只有成功后才清除 `hook_installed_` 并发送 HookState=false。失败向控制调用返回错误，保守保持已安装状态，便于重试/安全脱离。

新增回归：底层停止失败时命令失败且状态仍为已安装。

### 4. Winsock 地址参数存在异常指针崩溃窗口（中优先级）

`FormatIpv4`、`Ipv4Port` 和过滤上下文端口读取直接解引用来自目标应用的 `sockaddr*`。这些参数来自被 hook 的 API，异常指针可能触发访问违规，C++ `catch` 无法可靠拦住。

修复：先通过现有 SEH 安全复制函数 `TryCopyMemory` 复制到本地 `sockaddr_in`，再检查族和端口；不改变正常 IPv4 结果。

### 5. 宿主 Target 事件解码缺少边界/协议完整性检查（中优先级）

Stats 的行数、Dropped/Log/Fatal 的尾部字段以及未知事件原先存在宽松处理，协议错误可能被静默吞掉，或导致不必要的循环。

修复：

- Stats 的 filter/send/robot 计数限制为 `0..100000`。
- Dropped、Log、Fatal 强制无尾部字段。
- 未知事件改为显式错误并转成 UI toast。

## 仍需单独处理的风险/未完成项

这些不是本轮隐藏的失败，而是当前工程边界：

1. 注入成功但随后 IPC 建链失败时，目标进程内的 DLL 回收/远程线程回滚仍需专门设计；当前连接层会断开并清理本地会话，但不会强行卸载目标进程中的模块。
2. MinHook 在极端线程长期停留于 detour 时，`QuiesceAndShutdown` 采用安全重试/后台回收策略，不能保证同步瞬时完成；这是避免目标崩溃的保守策略。
3. 真实封包采集、滤镜执行器、发送/机器人执行器、代理运行时仍未实现；本轮没有把这些未完成模块伪装成已完成。
4. WebView2 Runtime 仍是运行依赖；若机器没有 Runtime 或包旁 `wwwroot` 被移动，宿主会明确报错而不是显示空白页面。
5. 当前自测中的 `editorRestartPersistence=false` 属于既有非门控编辑器自测字段，不影响本次 `result=passed`；若要把它变为强断言，需要另开数据重启场景修复。
